# Админка сайта ESP

Адрес: **https://esp-websitetest.vercel.app/admin**

Заказчик правит содержимое сам, разработчик не нужен. Изменения появляются
на сайте сразу после нажатия «Сохранить» — пересобирать и выкладывать ничего
не надо.

---

## Как это работает

1. Открыть `/admin`, ввести пароль.
2. Выбрать блок.
3. Раскрыть нужную запись, поправить поля. Видео и фотографии загружаются
   кнопкой «Загрузить» прямо из формы — путь подставляется сам.
4. Стрелки ↑ ↓ меняют порядок, ✕ удаляет запись, «+ Добавить» создаёт новую.
5. «Сохранить». Пока правки не сохранены, в шапке горит «есть несохранённые
   правки», и уйти со страницы браузер не даст без подтверждения.

Кнопка **«Вернуть как было»** откатывает весь блок к состоянию на момент
передачи сайта. Это защита от неудачной правки: исходный текст всегда лежит
в сборке и никуда не пропадает.

## Что уже настроено (это к разработчику)

Обе переменные уже заданы в проекте, хранилище создано и подключено.
Раздел оставлен на случай переноса проекта или смены пароля.

Без этих переменных админка на боевом адресе не работает — сделано
намеренно, чтобы публичный адрес не пускал кого угодно.

### 1. Пароль

```bash
vercel env add NUXT_ADMIN_PASSWORD production
```

Пока переменная не задана, `/admin` на проде отвечает
«Админка не настроена» и не пускает никого. Локально (`npm run dev`)
вход свободный — это удобно для разработки и безопасно, потому что
локальный адрес наружу не смотрит.

### 2. Хранилище правок

На Vercel файловая система только для чтения, поэтому правки уезжают
в Vercel Blob. Нужно создать хранилище и подключить его к проекту:

```bash
vercel blob store add esp-content
```

После этого Vercel сам добавит в проект переменную `BLOB_READ_WRITE_TOKEN`.
Бесплатного тарифа хватает с запасом: правки — это текстовые файлы,
объём считают загруженные видео и фотографии.

Проверить, что всё встало:

```bash
vercel env ls production
```

Пока `BLOB_READ_WRITE_TOKEN` не задан, в шапке админки горит жёлтая плашка
**«локальный режим»** — правки сохраняются в папку на компьютере разработчика
и на боевой сайт не попадают.

## Задержка появления правок на Vercel

Правка сохраняется сразу, но на сайте появляется **не мгновенно: обычно за
несколько секунд, иногда до минуты**.

Причина в хранилище, а не в админке. Vercel Blob не гарантирует, что сразу
после записи все обращения вернут новую версию: сохранение и отрисовку
страницы выполняют разные функции, и они могут обращаться к разным узлам
сети доставки. Кэш публичных файлов Vercel не опускает ниже 60 секунд.

Замерено на боевом сайте: запись возвращает ответ за 1,5 секунды, из них
до 1,2 секунды уходит на попытку убедиться, что хранилище уже отдаёт
записанное. Примерно в четверти случаев это удаётся сразу, в остальных —
позже.

Поэтому админка после сохранения говорит по факту:

- «Сохранено. Обновите страницу сайта» — хранилище уже отдаёт новое;
- «Сохранено. Хранилище ещё обновляется» — данные записаны, на сайте
  появятся через несколько секунд.

На работу заказчика это не влияет: человек сохраняет правку и смотрит
результат не в ту же секунду. Убрать задержку можно двумя способами:

1. **Дождаться переезда на HOSTER.by.** Там правки пишутся в файл на диске,
   задержки нет вообще, в коде менять ничего не нужно. Проверено на
   production-сборке с внешней папкой.
2. **Подключить Redis** (Upstash через маркетплейс Vercel, бесплатного
   тарифа хватает). Строго согласованное хранилище — правка видна сразу.
   Нужна одна переменная окружения и правка `server/utils/contentStore.ts`,
   работы примерно на полчаса.

## Переезд на HOSTER.by

Админка к Vercel не привязана. Драйвер хранилища выбирается переменными
окружения, прикладной код обоих случаев не различает, поэтому переезд —
это настройка, а не переделка.

Что поменяется:

| | Vercel (сейчас) | HOSTER.by (потом) |
|---|---|---|
| Правки | Vercel Blob | папка на диске |
| Загруженные файлы | адрес в Blob | маршрут `/media/**` |
| Переменные | `BLOB_READ_WRITE_TOKEN` | `CONTENT_DIR` |

На сервере нужно:

```bash
CONTENT_STORAGE=fs
CONTENT_DIR=/var/www/esp-content
NUXT_ADMIN_PASSWORD=<пароль>
```

`CONTENT_DIR` обязательно **вне каталога приложения**. При выкладке новой
версии каталог заменяется целиком — если правки лежат внутри него, они
пропадут вместе со старой версией. По этой же причине загруженные фото и
видео складываются туда же, а не в `public/`, и отдаются маршрутом `/media/**`.

Перенос уже сделанных правок — это копирование папки:

```bash
vercel blob list
```

скачать файлы из Blob и положить их в `CONTENT_DIR` с той же структурой
(`*.json` в корень, медиа в `uploads/`). Ссылки на медиа внутри JSON будут
вести на старые адреса Blob — их нужно заменить на `/media/<имя файла>`.
Если к моменту переезда правок ещё нет, делать не нужно ничего.

Сайт — Nuxt в режиме SSR, ему нужен Node на сервере (не «просто PHP-хостинг»).
На HOSTER.by это VPS или тариф с поддержкой Node.js.

## Как это устроено внутри

- `content/defaults/*.json` — то, что уехало в сборку. Это исходное состояние
  и одновременно запасной вариант: если хранилище недоступно, сайт отдаёт
  именно эти данные и продолжает работать.
- `server/utils/contentRegistry.ts` — список блоков и полей. Чтобы добавить
  в админку новое поле, достаточно дописать строку сюда: форма и проверка
  на сервере строятся по этому же описанию.
- `server/api/site-content/[key]` — публичное чтение, отсюда контент берут
  страницы сайта.
- `server/api/admin/*` — запись, закрыта паролем.
- `composables/useEditableList.js` — то, через что страницы получают
  редактируемые списки.

Поля, которых нет в описании блока (`slug`, контакты сотрудника, разделы
статьи), админка не показывает и не трогает — они переносятся из исходной
записи без изменений. Сломать через админку то, чего она не показывает,
нельзя.
